02 — SentinelNodeMonitoring & automation

Know when a service fails.
And when the signal stops.

HTTP monitoring with incident history and a separate signal for telemetry freshness. Missing observations become unknown, so yesterday’s green status can’t pass for today’s health.

PythonConcurrent HTTP checksGitHub ActionsTerraform
Run the incident lab ↗Read the source ↗

Self-directed project · Verified local incident lab. AWS deployment configuration is prepared; live AWS operation remains unverified.

The workflow

Check → detect → record → recover. Keep service health separate from reporting freshness.

The decision

When telemetry stops, mark the observation as unknown and suppress misleading health counts.

The evidence

46 checks across application behavior, browser flows, freshness handling, and infrastructure configuration.

Inspect the checks ↗
Inside the incident lab +

Recovery doesn’t erase the outage.

The local lab controls real HTTP fixtures: healthy responses, a slow service, an HTTP 503, and recovery. Aging an observation demonstrates a stale reporting signal separately. Resolved incidents remain in the timeline.

Repeatable, with clear limits.

The recorded sequence and automated checks let someone reproduce the behavior. Terraform describes a private S3 origin, CloudFront delivery, and a scheduled monitoring function. That cloud configuration has been checked, but hasn’t been verified in a live AWS deployment.
